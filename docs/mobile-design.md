# Android mobile boards

The user chose [mymind's mobile visual style](https://mymind.com/mobile), with adjustable preview sizing and aligned rows/columns like desktop Papan, then requested desktop's green accent and Instagram Explore's viewing experience. The interaction reference is a dense media grid, full-screen viewing on tap, swiping between pins and playback in place. Papan retains its own identity and standard Android Material behavior. Reading this as a private reference board for visual collectors, in a quiet notebook style with Papan's regular grid and Explore-style viewing: ENERGY 1 / RHYTHM 1 / MOTION 1.

Warm off-white separates white content cards with little framing; charcoal surfaces provide the same hierarchy in dark mode. Desktop's green identifies actions and selection: dark primary is `#D0F5AD`, matching desktop, and light primary is `#46662D` so it remains readable on light surfaces. Material foreground/container roles preserve contrast. The native scalable sans-serif keeps captions and controls legible. Papan's wordmark, collection strip and regular board supply the identity. Google's outlined Material phone/desktop/history/search/tune/add vectors replace the old framework icons; each names its real action or destination. No generated identity imagery is introduced.

Compact windows use Material bottom navigation for On phone, Desktop and Activity. Windows at least 600dp wide use a navigation rail. A compact toolbar holds Search and Board appearance; Paste link and secondary collection/connection actions live in its menu. Search appears when requested and Android Back closes it before leaving the board. A 56dp floating Add link action keeps capture available without a wide button over the collection. The duplicate collection heading is removed from ordinary boards. System, keyboard and floating-action insets reserve their own space.

RecyclerView uses equal-width columns, shared media frame proportions and 8dp gutters. New phone preferences aim for three columns at normal text size; explicit saved size choices remain unchanged. Desktop collections use their optional authenticated `preview.aspectRatio` and default frame fit, calculated across the complete collection using the desktop layout rule. Portrait collections keep vertical frames; cover mode stays square. Phone collections and older desktops retain square frames. Extremely short frames reserve enough height for readable captions. Each title and source website sit inside the bottom of the preview; there is no separate caption block. The caption follows desktop Papan's `.tile-overlay`, `.tile-title` and `.tile-source` treatment: a continuous transparent-to-65%-black fade with a 55% midpoint, regular 12sp white title, 10sp near-white source, 5dp between labels, 15dp side insets and 16dp bottom inset. The caption container has no background. Both labels always use one line with end ellipsis, and website names omit `www.`. The user requested a lighter backdrop: reduced opacity shows more media, while brighter labels retain readable contrast over a white image. Its 50dp lead-in scales with the user's font size. This gradient serves media/text readability, with no flat opacity plateau. Captions stay visible on touch screens; desktop's hover reveal has no phone equivalent. Full title text remains available to accessibility and in details, where Open source retains the complete URL. Mixed image proportions, long titles, loading and failed previews cannot change row heights within a collection. The caption fade measures at its natural height even when the media frame is short; only its transparent lead-in can extend outside the clipped frame, preserving both single-line labels. Video/link/text placeholders use the same square frame and overlay; loading or failure status stays in the preview area while the website remains visible. Board appearance contains a native Material Preview size slider, Fill image frames switch, and Use phone setting/Light/Dark radio controls. Smaller frames fit more columns; larger frames fit fewer. Below 340dp, or when enlarged text cannot fit multiple readable cards, the grid uses one column. Width changes use the actual board area, including the tablet rail. Resizing retains the visible reference and off-screen cards recycle normally.

Preview size and frame fit are phone-only view preferences keyed by location and collection ID. The last selected collection IDs survive reopening. These preferences are separate from the local library, pending delivery, desktop collection settings and receiver protocol. Theme follows Android by default and can be changed explicitly; a theme change recreates the Activity through AppCompat's normal lifecycle, without clearing the running app session.

Paste and Android share intents use the same Material bottom sheet to choose a phone or desktop collection. Forms and confirmations use Material dialogs, outlined text fields, field errors and native password visibility controls. Cards, buttons, navigation and snackbars use actual Material components rather than drawn imitations. Connections keeps pairing/recovery messages as plain text inside the dialog, scrolls them into view and exposes a polite accessibility live region. Board messages wait while another form is open; existing snackbars dismiss when the board loses focus. Controls retain at least 48dp touch targets. Text/error/status states accompany loading, empty, offline and failed-media states. Font scaling, accessibility descriptions and native focus/press feedback remain enabled.

On phone and Desktop are separate locations. Local collections and captured previews live in app-private storage and work without pairing. Choosing a phone destination commits the link before preview retrieval. Desktop shows only currently open collections, behind an explicit browsing preference. Choosing a desktop destination stores its stable ID with the pending link, including across restart and IP-address changes. A retry never silently switches to the desktop default. Legacy servers and offline default delivery remain explicitly labelled choices.

**Connections → Pair desktop** opens a native Material Nearby desktops dialog. Choose a discovered computer, compare the large six-digit code and explicitly allow pairing in desktop Papan. The request expires after two minutes; Cancel, backgrounding or QR fallback stops the phone worker and cancels unfinished requests. **Scan QR** remains available without discovery. Reconnecting the existing computer works with pending links; replacing it with a different computer remains blocked until those links are resolved. One desktop is active at a time.

Browsing and delivery recover a changed address through Android's native DNS-SD service. The phone verifies a fresh identity challenge using its existing pairing before saving a discovered endpoint; no bearer token is sent to an unverified discovered address. Recovery retains the key and each queued link's ID/destination. A concurrent manual address edit takes precedence over stale discovery. This reconnects the desktop connection; phone and desktop libraries remain separate.

Protected desktop contents require phone-specific password authorization even if the desktop already unlocked them. A random `X-Papan-Session` identity stays in memory across backgrounding, rotation and theme changes. Closing the main Activity ends it and requests scoped authorization removal; a killed process starts with a different identity even if its close request could not reach desktop. Passwords and session identities are never saved. Matching desktops retain access for that app session without the former 15-minute timeout. Desktop lock/close/revoke, protection changes and restart still block further reads; legacy clients keep their 15-minute grants. Backgrounding clears protected views and stops playback while retaining the session. Protected boards, passwords and details use Android's secure-window flag. Android Activity shows pending deliveries and offers explicit retry/dismiss actions.

Rotation/resizing recreates the Activity without revoking the desktop password grant. The replacement Activity restores its selected location/collection, reloads through the existing authorization and applies the secure-window flag before showing protected media. An actual app close clears authorization; a temporary Activity stop does not. Native checks rotate the isolated display both ways and verify decoded protected thumbnails remain visible; temporary backgrounding retains access, while close/reopen requires the password again.

Remote video cards use the desktop's optional authenticated `thumbnailUrl`: a bounded still-image cover from saved video media, with a small outlined Material play indicator. Local video covers use Android's native frame decoder. Titles/source websites retain the same lighter fade inside aligned collection-shaped bounds. Playback keeps the existing authenticated video URLs. Image cards can use the same thumbnail route; older providers retain the existing image-preview fallback. Thumbnails are delivered through the paired HTTP connection and collection access rules; discovery advertises the receiver address and identity only.

Desktop supplies the collection's known frame proportions and `measuredCount`. When saved video dimensions are absent, decoded covers contribute their dimensions to the shared frame calculation, matching desktop's measurement of displayed media. Measurements remain bounded in memory and clear with their protected thumbnails. Frame changes retain the visible reference. Loading and text-only placeholders use the collection's current frame proportions.

Local capture saves ordinary HTML titles and Open Graph thumbnails, plus direct JPEG/PNG/WebP/GIF images and MP4/WebM files up to 32 MiB. It does not run desktop's site-specific extractors or JavaScript. Failed capture retains the link and supports retry. There is no implicit synchronization; sending a local pin to desktop is explicit. Local collection encryption and `.papan` import/export are outside this version.

Guidance: [Android adaptive navigation](https://developer.android.com/develop/ui/views/layout/build-responsive-navigation), [Android dark theme](https://developer.android.com/develop/ui/views/theming/darktheme), [Android accessibility](https://developer.android.com/design/ui/mobile/guides/foundations/accessibility), [native network service discovery](https://developer.android.com/develop/connectivity/wifi/use-nsd), and [Material Components for Android](https://github.com/material-components/material-components-android/tree/1.13.0). Native verification and its limits are recorded in [verification.md](verification.md).

Tapping a pin opens a full-screen viewer with a compact Material toolbar and a fitted media stage. A cached board image appears immediately while the full-resolution image loads. Videos retain their still cover until the first decoded frame, then autoplay and loop in place; tap the video or use Play/Pause, and seek using the Material slider. Portrait and landscape media keep their aspect ratio. Images support pinch/double-tap zoom; keyboard activation toggles zoom and arrow keys pan a zoomed image. Vertical swipes move between pins in the current filtered collection, fetching another desktop page when needed. Horizontal swipes and Previous/Next buttons move between a pin's attachments; the toolbar menu provides Previous pin/Next pin alternatives. Details opens a separate sheet for the full title, source, notes and existing edit/save/retry/delete actions. Viewer position and playback state restore through configuration recreation, without saving protected content in Activity state. Loading, playback errors, Retry and collection boundaries have visible states inside the viewer.

Already decoded previews stay in a memory-only LRU cache, bounded by the smaller of 32 MiB or one eighth of the app heap. Concurrent loads of the same preview share work; recycled cards receive cached bitmaps synchronously. Cache keys separate desktop collection/session/URL and local file modification/size, as well as board/viewer resolution. Configuration recreation retains this cache. Locked, closed, revoked or unavailable desktop collections discard their cached and pending remote previews before showing contents. Closing the app clears the cache and cancels workers; no remote bytes enter the phone's disk cache. Refresh desktop explicitly drops remote previews to fetch changed media at stable URLs.

Lifecycle and cache guidance: [Activity lifecycle](https://developer.android.com/guide/components/activities/activity-lifecycle), [VideoView](https://developer.android.com/reference/android/widget/VideoView), [LruCache](https://developer.android.com/reference/android/util/LruCache), [Android immersive content](https://developer.android.com/design/ui/mobile/guides/layout-and-content/immersive-content).
